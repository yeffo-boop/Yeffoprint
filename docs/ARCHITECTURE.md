# YeffoPrint — Architecture

Companion to `PROJECT_SPEC.md`. This file explains *how* the system is structured, not *what* it should do. Keep it current as implementation decisions are made — future Claude Code sessions should be able to onboard from this file alone.

## 1. Two-Codebase Split

```
yeffoprint/          # block theme — presentation only
yeffoprint-core/      # plugin — business logic, data, pricing, orders
```

**Rule of thumb:** if it would still need to exist under a different theme, it belongs in `yeffoprint-core`. If it's purely how things look/lay out, it belongs in `yeffoprint`.

### `yeffoprint` (theme) owns
- `theme.json` design tokens (color, spacing, radius, typography)
- Block templates and template parts (FSE)
- Reusable block patterns (hero, featured designs, materials grid, etc.)
- Header/footer/announcement bar presentation
- WooCommerce template overrides for presentation only (product cards, cart drawer markup, checkout layout)
- Configurator **UI** (rendering, styling, preview surfaces) — consumes state/data from plugin-provided APIs, does not own pricing or schema logic
- Responsive/accessibility CSS and JS behavior for presentation components

### `yeffoprint-core` (plugin) owns
- Custom post types / data records: Templates, Materials, Sizes, Pricing Rules, Custom Orders, Proofs
- Template field-schema engine (generic, not compound/strength-specific)
- Pricing engine (base price, surcharges, bulk discount tiers, server-side authoritative calculation)
- Batch/variant data model and validation
- Cart/order metadata structure (how customization state is serialized and reconstructed)
- Custom order + proof workflow and status model
- REST/AJAX endpoints the configurator calls (fetch template schema, live price calc, submit custom order, etc.)
- Admin UI under a top-level **YeffoPrint** menu (Templates, Materials, Sizes, Pricing Rules, Custom Orders, Proofs, Site Settings)
- Seed/demo data tooling (dev-only, never auto-overwrites production content)
- Future: saved designs, reorder, rewards, sticker infrastructure

**Never:** business logic (pricing math, schema validation, order state transitions) inside the theme. Never core WordPress/WooCommerce file modification.

## 2. Core Data Model

```
Template
 ├─ id, name, active/inactive, featured, popularity/sort
 ├─ artwork, gallery imagery, vial mockup imagery
 ├─ tags: searchable / color / style / material-compatibility
 ├─ field_schema[]            # generic — see below
 └─ compatible_sizes[], compatible_materials[]

Field (within a Template's field_schema)
 ├─ id, label, type, default, required
 ├─ max_chars, position, alignment
 ├─ font_size_max, font_size_min, formatting_rules
 └─ admin_description, preview_behavior

Size (admin-managed record)
 ├─ id, name, active/inactive
 ├─ print_dimensions
 └─ price_adjustment

Material (admin-managed record)
 ├─ id, name, description, swatch/image, active/inactive
 ├─ price_adjustment
 ├─ compatible_products
 └─ sort_order

PricingRule
 ├─ base_unit_price
 ├─ size_surcharges[], material_surcharges[]
 ├─ bulk_discount_tiers[]   # threshold, type(percent|fixed_unit_price)
 └─ custom_design_fee

Batch (a single line item's shared config)
 ├─ template_id + version, size_id, material_id
 ├─ total_quantity
 ├─ pricing_snapshot            # rule version + computed breakdown
 └─ variants[]

Variant (one personalized label within a Batch)
 ├─ id, quantity
 ├─ field_values{}              # keyed by Field.id, per the template's schema
 └─ preview_state

CustomOrder (Fully Custom Design workflow — separate from Batch/Variant)
 ├─ size, material, quantity
 ├─ compound(s)/strength(s), brand name, style notes, instructions
 ├─ inspiration_uploads[]
 ├─ design_fee (fixed, $25 at launch)
 ├─ status  # Design in progress → Proof ready → Awaiting approval → Approved → Printing → Shipped
 └─ proof_history[]             # future portal: uploads, approvals, timestamps
```

**Design principle:** the schema is generic over field types — nothing in the data model or pricing engine should assume "compound" or "strength" specifically. Compound/strength are just two Fields defined on a given Template's schema.

## 3. Pricing Flow

1. Client (configurator JS) computes a **provisional** price locally from cached pricing-rule data for instant feedback.
2. On every state change that affects price, and always before Add to Cart / checkout, the client calls a plugin REST endpoint that recalculates from the authoritative `PricingRule` data server-side.
3. The server-computed value is what's stored on the cart item and order — client-submitted totals are never trusted.
4. Bulk discount tier is evaluated against the **batch's combined quantity** across all variants, not per-variant.

## 4. Preview Architecture

- Single source of truth: the active Batch/Variant state (JS state object, mirrored to a hidden form/cart payload).
- Label View and Vial View are two renderers subscribing to the same state — never separate data paths. Prefer SVG/structured HTML+CSS for Label View so text stays crisp and font-scaling can be computed precisely (measure against `font_size_min`/`max` before falling back to the overflow warning).

## 5. Cart & Order Metadata

Cart line items store structured metadata (not a single serialized blob), sufficient to:
- Re-render the exact configurator state for "Edit customization"
- Reconstruct the order for a future "Reorder" action
- Preserve which `PricingRule` version was active at time of purchase (so historical orders remain accurate even after prices change later)

## 6. Proof / Custom Order States

Modeled as a dedicated status field on `CustomOrder`, independent of WooCommerce's native order status, since the production/proof lifecycle (design → proof → approval → printing) doesn't map cleanly onto WooCommerce's processing/completed states. WooCommerce order status still drives payment/fulfillment; `CustomOrder.status` drives the production workflow and is surfaced to the customer and admin separately.

## 7. Key WordPress/WooCommerce Integration Points

- WooCommerce: product/catalog infra, cart, checkout, customer accounts, orders, WooPayments, shipping — used natively wherever it models the need adequately.
- Product-level customization (fields, batches, variants, pricing) is layered on top via `yeffoprint-core`, not via WooCommerce Product Variations (avoids the template × material × size variation explosion the spec explicitly rules out).
- REST/AJAX endpoints exposed by the plugin for: template schema fetch, live price calc, cart add w/ structured metadata, custom order submission + uploads.

## 8. Extensibility Points (built now, UI later)

- `CustomOrder` proof fields already shaped for a future customer-facing proof portal.
- Batch/Variant model already sufficient for a future "Reorder" (rehydrate into configurator) and "Saved Designs" (persist a Batch to a user without purchasing).
- Pricing/upload/option infrastructure intentionally generic so Custom Stickers (Phase 2) can reuse it rather than needing a parallel system.

## 9. Open Architectural Decisions

*(Log decisions here as they're made during implementation, with brief rationale — keep entries short.)*

- **Data records as CPTs (Phase 1):** Template, Material, Size, Pricing Rule, Custom Order, and Proof are implemented as custom post types (`yp_template`, `yp_material`, `yp_size`, `yp_pricing_rule`, `yp_custom_order`, `yp_proof`) with structured meta rather than custom DB tables. Rationale: native wp-admin list-table/CRUD UI for free, works with REST out of the box, no migration tooling needed at this stage. Revisit only if query patterns demand custom tables later.
- **Plugin bootstrap pattern:** single root plugin file (`yeffoprint-core.php`) that requires a `YeffoPrint_Core` singleton in `includes/class-yeffoprint-core.php`, which in turn loads one class per post type under `includes/post-types/`. Keeps registration declarative and easy for future phases (pricing engine, REST endpoints, admin screens) to hook into the same singleton without touching the bootstrap file.
- **Theme scaffolding (Phase 1):** minimal valid FSE block theme (`style.css` header + `theme.json` + empty `templates/index.html` + `parts/header.html`/`footer.html`) with design tokens (color palette, radius scale, typography, spacing) from PROJECT_SPEC §5 encoded directly in `theme.json`. No patterns or WooCommerce template overrides yet — those start in Phase 2/3.
- **Global UI tokens (Phase 2):** added shadow (`shadow-elevation.low/medium/high`), glassmorphism (`glass.background/border/blur`), and `focus-ring` tokens under `theme.json` `settings.custom`, plus a `spacingSizes` scale mirroring the existing `spacing-scale` custom tokens so the block editor's own spacing UI offers the same values. Button element styling (radius, padding, hover) set via `styles.elements.button` rather than a class, so it applies to every core Button block automatically.
- **Component CSS lives in one file (Phase 2):** `assets/css/global.css` holds all cross-page component styles (header, drawer primitive, cards, forms, footer, a11y utilities) enqueued via `wp_enqueue_scripts`. Section/page-specific styling will move into block patterns as they're built (Phase 3+); this file stays scoped to reusable chrome so it doesn't grow into a dumping ground.
- **Drawer primitive, not a cart-specific component (Phase 2):** built one generic accessible drawer (`.yp-drawer`, open/close/focus-trap/ESC in `assets/js/site.js`) used now for the mobile search overlay and stubbed for the cart. The Phase 7 cart drawer will populate `#yp-cart-drawer`'s body with real line-item markup (and swap in WooCommerce's cart-fragments data) rather than introducing a second drawer mechanism.
- **Mobile nav uses core Navigation block's built-in overlay** (`overlayMenu: "mobile"`) instead of hand-rolled hamburger JS — avoids extra JS for something WordPress core already handles accessibly, in line with the "minimal third-party dependencies" priority.
- **Account icon uses the WooCommerce `customer-account` block** (`icon_only` display) rather than custom account-menu markup, since Accounts (PROJECT_SPEC §16) isn't built until Phase 9 — the block already links to the native My Account page in the interim with no custom code required.
- **Shop Labels is the `yp_template` archive (Phase 3):** rather than a hand-built page template with a manual `WP_Query`, the Template CPT now registers `has_archive => 'shop-labels'` with a matching rewrite slug, so `/shop-labels/` *is* `templates/archive-yp_template.html`. Filters (Style/Color/Material) and sort both work by extending that one native archive query — see the next two entries — instead of introducing a parallel query layer.
- **Filters use native taxonomy query vars, sort uses `pre_get_posts` (Phase 3):** `yp_style`/`yp_color`/`yp_material_tag` are registered with matching `query_var`s, so `?yp_style=bold` filters the archive with zero custom code — WordPress folds it into the main query automatically. Sort (`?sort=featured|newest|popularity`) is resolved in `YeffoPrint_Template_Query::apply_shop_labels_sort()` (plugin, since it's query/business logic) via `pre_get_posts`. Both are plain GET requests with a working non-JS fallback, matching PROJECT_SPEC §6's "richer JS is justified [only in] the configurator."
- **Predictive search extends core search rather than replacing it (Phase 3):** on every Template save, `YeffoPrint_Template_Search` flattens title + style/color/material term names into a `_yp_search_index` post meta value, then splices an `OR (yp_search_index.meta_value LIKE ...)` into core's own `posts_search` SQL fragment (scoped to `yp_template` searches only). The same extended search backs both the classic `s=` query and the REST `?search=` param the header's predictive dropdown (`assets/js/search.js`) calls — one search implementation, two entry points.
- **Card presentation is a theme-owned dynamic block, not a Query Loop of core blocks (Phase 3):** `yeffoprint/template-card` (script-less, `render.php` only, per the WP 6.4 "render" block.json field) is what actually needs per-post plugin data — the vial-mockup hover-swap image and badge can't be expressed as static core block markup inside a Query Loop's Post Template. The plugin exposes that data through one template tag, `yeffoprint_core_get_template_card_data()` (`includes/api/template-api.php`), so the block never reads `_yp_*` meta keys or plugin class constants directly — it stays a presentation consumer of a plugin API, per the Architecture §1 split. `yeffoprint/gallery-toolbar` (the sort/filter bar) is the same pattern, server-rendered because it needs live `$_GET` state and term counts that static markup can't provide.
- **Starting price is a plugin template tag, not a literal string (Phase 3):** `yeffoprint_core_starting_price_label()` (`includes/pricing/class-pricing-placeholder.php`) wraps the `$0.35` base price constant so the theme card never hard-codes a price string, even though the real PricingRule-driven calculation doesn't exist until Phase 6. That file is deleted once Phase 6 lands.
- **Template meta (featured/popularity/badge/vial mockup) has no admin UI yet (Phase 3):** registered via `register_post_meta` with `show_in_rest` so it's settable through the REST API, WP-CLI, or the block editor's Custom Fields panel, but no meta box was built — Phase 4 ("Template Management") owns the admin CRUD experience and will replace this with proper controls. `wp yeffoprint seed` (dev-only WP-CLI command, idempotent by slug) seeds demo Templates so the gallery/filters/sort/search are actually exercisable before Phase 4 lands.
- **field_schema is a single JSON meta value, not per-key `register_post_meta` fields (Phase 4):** each Template's `field_schema` (array of field definitions — id/label/type/default/required/max_chars/position/alignment/font sizing/formatting rule/preview behavior/admin description) is stored as one JSON-encoded string in `_yp_field_schema`, validated by `YeffoPrint_Field_Schema::sanitize()` — not exposed via `register_post_meta`'s REST array schema. Reasoning: a REST-typed nested array-of-objects schema buys nothing yet, since nothing public reads it until Phase 5's schema-fetch endpoint, which can shape the JSON however the configurator actually needs it. The admin editor reads/writes it through the classic nonce-verified meta box POST flow, same as `compatible_sizes`/`compatible_materials` (also plain `get/update_post_meta`, same rationale).
- **Field-schema repeater reorders via Move Up/Down buttons, not drag-and-drop (Phase 4):** `assets/admin/field-schema.js` keeps the whole repeater keyboard-operable (PROJECT_SPEC §6 WCAG 2.2 AA target) rather than requiring pointer-based HTML5 drag-and-drop, which needs significant extra ARIA work to be accessible. Same vanilla-JS, no-build-step approach as the theme's JS — state lives in a plain in-memory array, every mutation re-renders and re-syncs one hidden JSON input that submits with the normal post form.
- **V1 field types are `text` and `textarea` only (Phase 4):** `YeffoPrint_Field_Schema::TYPES` is a single constant map nothing else depends on the shape of — extending it later (e.g. a `select` type) touches one array, not the sanitize logic, the repeater JS, or the save flow.
- **Position is two percentage inputs (x/y, 0–100), not a visual click-to-place picker (Phase 4):** matches PROJECT_SPEC §10 ("no freeform/drag-drop placement in V1") — admin sets a fixed position per field, customers never move it. A visual picker on top of the actual artwork is Phase 5 territory (it needs the Label View preview surface to exist first), not a Phase 4 admin-CRUD concern.
- **Material/Size lean on native WordPress fields instead of custom meta (Phase 4):** active/inactive is `post_status` (publish/draft) rather than a redundant boolean meta flag; sort_order is native `menu_order` (via `page-attributes` support, which also gives a built-in drag-orderable admin list for free); Material's description is `post_content` (via `editor` support); the swatch image is the existing featured-image (`thumbnail` support, already registered in Phase 1). The only new meta is `price_adjustment` (both) and Size's `print_width_mm`/`print_height_mm`. `compatible_products` from the Architecture §2 Material model isn't duplicated on Material — `Template.compatible_materials` (set from the Template editor) is the single source of truth for that relationship, read from the Template side only, so the two can't drift out of sync.
- **The "template schema fetch" endpoint is public and read-only (Phase 5):** `GET /yeffoprint-core/v1/templates/{id}/configurator` (`class-template-schema-controller.php`) needs no auth (`permission_callback` is `__return_true`) because everything it returns is already public storefront data — a published Template plus its published, compatible Sizes/Materials. It shapes `field_schema`/sizes/materials/pricing into exactly what the configurator needs, rather than the theme assembling that from three separate `wp/v2` REST calls. `base_unit_price` is still the Phase 3 placeholder constant — Phase 6 is what makes this endpoint's pricing authoritative.
- **Quantity presets (25/50/100/250/500/1000) live in the plugin, not the theme (Phase 5):** `yeffoprint_core_quantity_presets()` (`includes/configurator/quantity-presets.php`) is a fixed business rule from PROJECT_SPEC §10, not an admin-configurable record like Sizes/Materials — but it's still returned through the schema-fetch endpoint rather than hard-coded in `configurator.js`, so there's one source of truth if it ever needs to change.
- **Label View and Vial View render the exact same field DOM (Phase 5):** per Architecture §4 ("never a separate data source"), `configurator.js` builds one set of absolutely-positioned field elements from `field_schema` and only swaps the background image + toggles a CSS class between views — Vial View isn't a second render path. Because there's no per-template "where does the label sit on this bottle" data yet, Vial View approximates it with a flat `scale(0.55)` on the same field positions rather than a calibrated placement region. Revisit if/when Vial View needs to look convincing rather than illustrative — likely a new admin-configurable placement field on Template, not a configurator rewrite.
- **Font auto-scaling measures against a shared box ratio, not a per-field box size (Phase 5):** the Field data model has `font_size_min/max` and `position` but no explicit box width/height, so `fitText()` in `configurator.js` measures every field against a box that's a fixed percentage of the stage's own rendered size (86% width; 32% height, multiline fields only) rather than a per-field dimension. Shrinks the field's font from `font_size_max` down to `font_size_min` in 1px steps until it fits (or doesn't — then it gets the `is-overflowing` outline and the shared "Text is too long for this design" banner, per PROJECT_SPEC §10). If per-field box sizing turns out to matter, it's an additive schema field, not a rework of the fitting algorithm.
- **Provisional pricing only, still no server validation (Phase 5):** the configurator's running total (`unitPrice() × totalQuantity()`) uses `base_unit_price` plus whatever Size/Material `price_adjustment` the customer picked — real values already in the REST payload — but has no bulk-discount tiers and is never sent anywhere the server would trust it. "Server always recalculates/validates authoritative price" (PROJECT_SPEC §12) is Phase 6.
- **"Add to Cart" is a visible stub, not a disabled button (Phase 5):** since WooCommerce cart integration is Phase 7, both Add to Cart buttons (desktop summary panel + mobile sticky bar) are live and clickable but show an inline "Cart isn't connected yet" message rather than being permanently `disabled` — keeps the buttons testable/stylable now and is a one-line swap for the real cart-add call later.
- **`wp yeffoprint seed` now also creates the launch Sizes/Materials and wires each demo Template's compatible_sizes/compatible_materials/field_schema (Phase 5):** the Phase 3 version only seeded Templates, which left the configurator with nothing to render. Same idempotent-by-slug approach, extended to `yp_size`/`yp_material`.
- **PricingRule doesn't duplicate `size_surcharges[]`/`material_surcharges[]` (Phase 6):** even though docs/ARCHITECTURE.md §2 lists them there, that data already exists as `price_adjustment` on the Size/Material records themselves (Phase 4), admin-managed on the record they describe. `YeffoPrint_Pricing_Rule` only owns what doesn't belong anywhere else: `base_unit_price`, `bulk_discount_tiers[]`, and `custom_design_fee`. One source of truth per fact, same principle as the `compatible_materials` vs. `compatible_products` call in Phase 4.
- **Exactly one "active" PricingRule, not a versioned/selectable set (Phase 6):** `YeffoPrint_Pricing_Rule::get_active_rule_id()` uses the most recently modified published `yp_pricing_rule` post, auto-creating a default (matching the old placeholder's $0.35 base / $25 design fee) on first use so the site always prices correctly. A nondev just edits the one entry under Pricing Rules; nothing stops creating a second published one, but there's no reason to and the UI doesn't invite it. A `_yp_rule_version` meta increments on every save specifically so Phase 7/8 order metadata can snapshot which version priced an order (Architecture §5), without building full CPT-revision-based versioning now.
- **A `fixed_unit_price` bulk-discount tier sets the resulting per-unit price, not a flat amount off (Phase 6):** reconciles the tier-type name with PROJECT_SPEC §12's literal formula `(base + adjustments − discounts) × quantity` — `YeffoPrint_Pricing_Rule::calculate()` derives `discount_per_unit = (base+adjustments) − value` for that tier type, so the formula still holds structurally for either tier type (`percent` computes the discount as a share of the pre-discount price instead).
- **`/pricing/calculate` is template-agnostic (Phase 6):** takes `size_id`/`material_id`/`quantity`, not a template ID — size and material adjustments live on their own records and are shared by every variant in a batch (one template/size/material per batch, PROJECT_SPEC §10), so the calculation never needed template context. Public and read-only (no auth) since nothing it returns is sensitive and it has no side effects; Phase 8's Custom Order flow can call it unchanged rather than needing a parallel calculator.
- **The configurator shows an instant client estimate, then swaps in the authoritative breakdown (Phase 6):** `renderSummary()` in `configurator.js` renders the same provisional math as Phase 5 immediately (no network round-trip), then a 300ms-debounced call to `/pricing/calculate` replaces it with the real, discount-aware breakdown — implementing Architecture §3's two-stage pricing flow exactly. A monotonic request counter discards stale responses if the customer changes size/material/quantity again before the first call returns.
- **One WooCommerce simple product per Template, hidden from the shop (Phase 7):** resolves Architecture §7's "layered on top via yeffoprint-core, not via WooCommerce Product Variations" — one product per *Template*, not per template×size×material combination, avoiding the variation explosion PROJECT_SPEC §20 rules out. `YeffoPrint_Linked_Product` keeps it in sync on every Template save: `catalog_visibility` is `hidden` (customers only ever reach it through the configurator's Add to Cart, never WooCommerce's own shop/search), `manage_stock` is off with `stock_status` always `instock` (made-to-order, PROJECT_SPEC §15 — never "only X left"), and price is always `0` since the real price is computed live, never read from the product. Unpublishing a Template drafts its linked product; it's never hard-deleted, since past orders still reference it by ID.
- **One batch = one WooCommerce line item, quantity = the combined quantity across its variants (Phase 7):** matches PROJECT_SPEC §10 ("a batch shares one template/size/material") and Architecture §3.4 (discount tier evaluated against combined quantity) exactly — a batch never splits across multiple cart/order line items. The variant-level detail (each variant's own quantity and field values) lives inside that one line item's `yp_variants` data, not as separate lines.
- **Cart price is always live-recalculated, order price is a frozen snapshot (Phase 7):** `woocommerce_before_calculate_totals` re-derives every cart item's price from `YeffoPrint_Pricing_Rule::calculate()` using its *current* stored size/material adjustments and combined quantity — never a price cached at add-to-cart time — so an item sitting in a cart always reflects current pricing (PROJECT_SPEC §12: "server always recalculates"). At checkout, `woocommerce_checkout_create_order_line_item` freezes that calculation, plus Template/Size/Material snapshots, onto the order line item — satisfying Architecture §5's "preserve which PricingRule version was active at time of purchase" without needing a formal Template version-number system (there isn't one yet; a JSON snapshot of the Template's title + field_schema at order time serves the same purpose more directly).
- **Order item data is several named meta keys, not one blob — except `_yp_variants`, deliberately (Phase 7):** `_yp_template_snapshot`, `_yp_size_snapshot`, `_yp_material_snapshot`, `_yp_pricing_snapshot`, and `_yp_batch_quantity` are separate meta rows, matching PROJECT_SPEC §14's "never one opaque serialized blob." `_yp_variants` is still one JSON array, because a batch's variant list is inherently one repeating structured unit — the same reasoning already applied to `field_schema` in Phase 4. All five are hidden from the default order-meta display via `woocommerce_hidden_order_itemmeta`; separate human-readable rows (Size, Material, Labels in this batch) are added alongside them for the admin order screen and customer emails.
- **`woocommerce_get_item_data` is the only item-data mechanism needed — it already reaches the Cart/Checkout blocks (Phase 7, corrected post-launch):** originally assumed to be classic-template-only and documented as a "known gap" requiring a future Store API `ExtendSchema` integration. That assumption was wrong: WooCommerce core's own `CartItemSchema::get_item_data()` (`StoreApi/Schemas/V1/CartItemSchema.php`) calls `apply_filters( 'woocommerce_get_item_data', [], $cart_item )` directly and feeds the result into the Store API's `item_data` field that the Cart/Checkout blocks render — the same hook `YeffoPrint_Cart_Pricing::display_item_data()` already uses. Its only real restriction is that each value must be a scalar (non-scalar entries, i.e. anything with markup, are silently dropped), which our implementation already satisfies since it only ever emits plain-text key/value pairs. No integration work was needed; `assets/css/woocommerce.css`'s generic Blocks-class selectors already cover styling either page style renders. (A live cart inspected during debugging showed `item_data: []`, which looked like this gap — it turned out to be an unrelated cause: that cart line was a manually-added test product that never went through the configurator/`/cart/add` flow, so it had no batch data for `display_item_data()` to describe in the first place, classic or Blocks.)
- **The cart drawer is custom-rendered PHP (server-side), not the WooCommerce Mini Cart block (Phase 7):** PROJECT_SPEC §14 specifies exact drawer contents (template, thumbnail, size, material, quantity, price, Edit customization + Checkout/View Cart — nothing else, deliberately no inline remove/quantity controls) that would need deeper Store API/Blocks slot-fill work to reproduce precisely. Reuses the Phase 2 `.yp-drawer` primitive and `#yp-cart-drawer` shell instead: `GET /cart/drawer` and the `drawer_html` returned by `POST /cart/add` are server-rendered HTML fragments injected into that shell's body, keeping one drawer mechanism (not two) and exact control over markup — consistent with the classic-hooks choice above rather than mixing both WooCommerce integration paradigms.
- **"Edit customization" is remove-then-re-add, not in-place mutation (Phase 7):** a cart item's size/material can change on edit, so there's no clean way to mutate an existing WC cart item in place once its defining attributes change anyway. `configurator.js` reads `?edit=<cart_item_key>` from the URL, fetches that item's stored batch via `GET /cart/item/{key}`, and rehydrates the configurator from it; submitting sends `edit_key` back to `POST /cart/add`, which removes the old cart item before adding the new one — the standard, robust WooCommerce pattern for this, and avoids a second "update" endpoint.
- **A defensive `woocommerce_add_to_cart_validation` net, bypassed by a static flag (Phase 7):** `YeffoPrint_Cart_Pricing::allow_next_add()` is a static bool set immediately before and cleared immediately after the cart controller's one legitimate `WC()->cart->add_to_cart()` call — anyone reaching WooCommerce's native add-to-cart directly for one of these hidden linked products without going through `/cart/add` gets rejected with a clear notice. A static flag (not a `$_REQUEST` marker) because the filter fires on *every* `add_to_cart()` call including our own internal one, and REST JSON bodies don't populate `$_REQUEST`.
- **Shipping/taxes/WooPayments are WooCommerce admin configuration, not code (Phase 7):** PROJECT_SPEC §15's flat rates (US: USPS $6 / UPS $15; International: $25) are ordinary Shipping Zones — `wp yeffoprint setup-shipping` (dev-only WP-CLI command, idempotent by zone/method-existence check, same pattern as `wp yeffoprint seed`) configures them so this doesn't have to be clicked through by hand on every fresh setup, but there's no custom shipping logic anywhere. Taxes stay at WooCommerce's default (disabled) — nothing needed there beyond not interfering with it. WooPayments is a separate extension a site owner installs and connects a merchant account to; no custom payment code was written, and none is needed — checkout works with whatever gateways WooCommerce has configured.
- **CustomOrder payment status and production status are two different fields, reusing the Material/Size `post_status` pattern (Phase 8):** a CustomOrder starts `post_status = draft` at submission (unpaid) and flips to `publish` only once `woocommerce_payment_complete` fires for its linked order — at which point `_yp_status` (the six-state PROJECT_SPEC §13 pipeline: Design in progress → Proof ready → Awaiting approval → Approved → Printing → Shipped) is set to its first value. This is Architecture §6's "WooCommerce order status drives payment/fulfillment; CustomOrder.status drives the production workflow" made concrete: `post_status` *is* the payment gate, `_yp_status` only ever means something once that gate has passed.

Scoped to the theme's `functions.php` enqueue calls; the plugin's admin-only assets (`yeffoprint-core/includes/admin/*`) have the same never-bumped-version pattern but weren't touched here — lower risk (wp-admin is rarely behind the same caching layers) and out of scope for this specific report.
- **The configurator's preview stage now matches each view's actual image shape instead of forcing both into one fixed square (live-site bugfix):** `.yp-configurator__stage` was a single `aspect-ratio: 1` box for both Label View and Vial View, with `object-fit: contain` — since real label artwork is 15:7 (rectangular, same ratio as the shop gallery cards) not square, it got shrunk to fit inside the square box, leaving visible gray letterboxing on the sides (the box's own background color, showing through wherever the image doesn't reach). Label View is now `aspect-ratio: 15/7` by default, with `[data-view="vial"]` overriding back to `1` — each view's box now matches what's actually meant to be uploaded to it, no code needed to detect the uploaded image's own dimensions since `field.position` percentages and `fitText()`'s box-fit math already read the stage's live rendered size rather than a hardcoded value (unaffected by this change). Also documented the expected upload sizes at the point of upload: a hint under the Template's featured-image box (`admin_post_thumbnail_html` filter, scoped to `yp_template`) for the 15:7 label artwork, and an updated description under the Vial mockup image field noting it's square for Vial View but also doubles as the gallery card's rectangular hover-swap image — a square mockup will letterbox in that second, unrelated slot, which is expected and only affects the hover-swap, not Vial View itself.
- **`.yp-card-grid` switched from `auto-fit, minmax(…,1fr)` to fixed-width `auto-fill` columns — the previous fix for a sparse row (one card, four columns) introduced a different misalignment bug for a *partially* full row:** with `1fr` tracks, each card's own grid cell stretched to share the row's full width, so with e.g. 2 cards in a nominally-4-column row, card 2 sat at the start of its own (very wide) second cell — far to the right of card 1, not next to it, since the `max-width: 320px` cap on `.yp-template-card` only capped the *card*, not the cell it was left-aligned within. `repeat(auto-fill, 270px)` uses fixed-width tracks instead: every card is the same width and sits immediately next to the last one regardless of count, and unused row space is simply blank at the end rather than distributed into cells — still fully responsive (auto-fill fits as many 270px columns as the viewport allows, same as before). The per-card `max-width` cap is gone too; it's redundant now that the column itself is a fixed size.
- **Header background made bolder per direct feedback ("just gray... can we be more creative, something with CMYK color, something that pops"):** the flat `rgba(20,20,20,0.88)` picked up two layered radial-gradient glows (cyan top-left, magenta bottom-right, same technique as the hero and dark CTA sections) instead of a flat color, plus a 2px CMYK gradient line along the bottom edge (`gradient-brand`, the same token used on card accent bars) replacing the plain `rgba(255,255,255,0.08)` border. A "Deployer for Git" banner visible in the screenshot that prompted this initially looked like a mid-deploy artifact explaining a mismatched light-header/light-text render — the user clarified it was an unrelated window behind the screenshot, not the site, so that render was real and not a deploy-timing artifact. The likely actual explanation (flagged to the user, not yet confirmed): WordPress stores template-part edits made through Appearance → Editor in the database, permanently overriding the theme file from then on — if `parts/header.html` was ever opened and saved there, the DB copy, not this repo's file, is what renders, and no amount of git-committed CSS/HTML changes would be visible until that override is cleared.
- **Nav links restyled as visible pill/buttons, cache-busting switched from filemtime to a content hash (live-site feedback: "can't see the text... make them look like buttons," cards still misaligned after the auto-fill fix):** `.yp-header__nav` links now get a translucent-white pill background (`rgba(255,255,255,0.1)`, brightening on hover) instead of relying solely on text-color contrast against the dark header — directly requested ("style the links better, make them look like buttons"). For the card grid, no further structural bug was found on inspection (the `auto-fill, 270px` fix from the previous entry is correct CSS); `justify-content: start` and `align-items: start` were added to `.yp-card-grid` explicitly as a defensive measure removing any ambiguity, and `yeffoprint_asset_version()` (`functions.php`) switched from `filemtime()` to `md5_file()` (truncated to 12 chars) — some git-based deploy tools don't reliably bump a file's modified-time on checkout, which would silently reintroduce the exact stale-cache problem the filemtime fix was meant to close, on a per-deploy-mechanism basis that's invisible from this codebase. (2) A drag-to-position preview in the "Customization Fields" meta box (`assets/admin/field-schema.js`, `#yp-field-position-preview`) shows the Template's actual featured image with one draggable marker per field, labeled by the field's own label — dragging a marker updates that field's `position.x`/`position.y` (and vice versa: editing the raw percentage inputs live-updates the marker), so "where will this land" is answered by looking at the real artwork instead of guessing two blind percentages. The numeric inputs stay for exact adjustment; nothing about the stored data shape changed, so this is presentation-only on top of the existing `position: {x, y}` schema. Matches Architecture §9's Phase 4 note that a visual picker was intentionally deferred "until the Label View preview surface exists" — it does now (Phase 5's configurator), so this was always meant to land as a follow-up, not a new decision. The plugin's admin-only assets (`admin.css`, `field-schema.js`, `pricing-tiers.js`, `vial-mockup-picker.js`) also picked up the same content-hash cache-busting (`yeffoprint_core_asset_version()`, `yeffoprint-core.php`) as the theme got two entries above — flagged then as lower-risk and out of scope, but landing new admin JS right now made it the right moment to close that gap too, so the new picker doesn't risk the exact stale-cache problem that prompted the theme-side fix.

## V2 (V1's PROJECT_SPEC §19 non-goals, built one at a time)

Direct request: "onto v2 — saved designs UI, one-click reorder UI, online proof approval UI, rewards dashboard, referral system." Five separate features; building them all in one pass would break the phased-validation discipline the whole V1 build followed and be too much to review together. Sequenced as: Saved Designs and one-click Reorder first (both reuse existing rehydration/snapshot infrastructure directly, lowest ambiguity), then Proof Approval (moderate — customer-facing state changes plus staff notification), then Rewards and Referral last, since those need real business-rule decisions (points-earning formula, redemption mechanics, referral payout amounts) that can't be invented unilaterally — those get asked about when their turn comes, not guessed now.

- **Saved Designs is real (first V2 feature):** Architecture §8 anticipated this exact shape ("Batch/Variant model already sufficient for a future... 'Saved Designs' (persist a Batch to a user without purchasing)") — a new `yp_saved_design` CPT (customer-owned via native `post_author`, not a custom `_yp_customer_id` meta field like CustomOrder needs, since a saved design is always created by the logged-in customer who owns it, never before that's known) stores `{template_id, size_id, material_id, variants}`, the identical shape a cart item and order line item snapshot already use. `YeffoPrint_Saved_Design_Controller` exposes create/list/fetch/delete over REST, all requiring login (nothing to attach an anonymous save to) with item-level ownership checks on fetch/delete. Fetching one saved design returns the exact same `{template_id, size_id, material_id, variants}` shape `GET /cart/item/{key}` and `GET /orders/{id}/items/{id}` already return, so `configurator.js`'s existing `hydrateFromBatch()`/`loadExternalBatch()` needed only a third source URL (`?saved=<id>`) added alongside `?edit=`/`?reorder=`, not new rehydration logic.

It's always rendered; `functions.php` localizes `isLoggedIn`/`accountUrl` alongside the existing nonce, and `configurator.js` relabels it to "Log in to save this design" (redirecting to My Account on click) rather than showing a button that would silently fail or need a confusing error message for a guest.

Handled on `template_redirect` — before any theme output starts — specifically so a real `wp_safe_redirect()` back to a clean URL is possible after deleting, avoiding a resubmit-on-refresh POST sitting in the customer's browser history the way processing it inline during the tab's own render (after output has already started) would have.

## Custom Stickers (PROJECT_SPEC §19 non-goal, now in scope)

Direct answers on the three open questions before building: pricing is preset size tiers (not a pure $/sq-in formula, not a manual-quote flow), the order flow requires a staff-uploaded proof before production (reusing the CustomOrder/Proof machinery Custom Design already validated), and "Custom Shape" means contour-cut to the artwork's own outline — no separate cut-path upload. Built in stages like every other phase here; this entry covers stage one (data model + admin), landed before any customer-facing form exists yet.

- **`yp_custom_order` gets a `type` field rather than a parallel CPT — the single biggest reuse decision:** `YeffoPrint_Custom_Order_Meta::ORDER_TYPE` (`'label'`, the default every pre-existing record implicitly has since the meta row doesn't exist yet, or `'sticker'`) means Custom Stickers inherits payment gating (`post_status` draft→publish on paid), the six-state proof pipeline, guest access tokens, `YeffoPrint_Secure_Upload`'s validated uploads, the Proofs My Account tab, and Reorder — all of it, unmodified — exactly the "generic infrastructure... so Custom Stickers can reuse it rather than needing a parallel system" §8 called for. `SIZE_ID`/`MATERIAL_ID`/`QUANTITY` are reused as literal meta keys for both flows too (a size/material/quantity is that regardless of product; `SIZE_ID` points at a `yp_size` post for a label order and a `yp_sticker_size` post for a sticker one — every reader already has to branch on `ORDER_TYPE` anyway). New sticker-only meta: `STICKER_TYPE` (sheet/die-cut), `SHAPE`, `CUSTOM_WIDTH_IN`/`CUSTOM_HEIGHT_IN` (only meaningful when `SIZE_ID` points at the custom tier), and `ARTWORK_UPLOADS` — deliberately a separate field from `INSPIRATION_UPLOADS`, since a sticker order's file is the actual print-ready artwork, not a label order's "here's what I'm going for" reference image.
- **A new `yp_sticker_size` CPT, not a reuse of `yp_size` — the one place reuse was rejected, on purpose:** `yp_size.price_adjustment` is a small delta on top of a shared $0.35/label base; a sticker size tier's price *is* the base for that sticker, an order-of-magnitude different meaning. Reusing the same field/record type would have blurred two distinct pricing models together the exact way §9's Phase 6 entry warns against duplicating a fact across records. One tier can be flagged `is_custom` (`YeffoPrint_Sticker_Size_Meta::IS_CUSTOM`) — the admin editor enforces at most one by clearing the flag on every other record on save, so `get_custom_tier_id()` never has to pick among several. This is how "preset tiers" (the chosen pricing model) still prices a genuinely custom dimension live, at checkout, before the proof step: the customer types exact inches on that one tier, and price is computed from an admin-set $/sq-in rate instead of a stored flat price — reconciling "preset tiers" with "sizes can be very custom" rather than treating them as a contradiction.
- **`YeffoPrint_Sticker_Pricing` is a separate formula from `YeffoPrint_Pricing_Rule::calculate()`, not a reuse — same reasoning as the CPT split above:** the label formula's "base" is one global per-label constant with material/size as small adjustments; a sticker's base is already the size tier's own (fixed or computed) price. Calling the label formula with a sticker's numbers would either silently add the label's $0.35 onto every sticker or require awkwardly zeroing it out. Kept the same *shape* deliberately though — `(size base − discount) + material/type/shape adjustments, × quantity`, discount computed from the base only and never allowed to shave an adjustment, bulk tiers resolved against a combined quantity — because those are the pricing *principles* this site already committed to (PROJECT_SPEC §12, the Phase 6 "discount never touches an upcharge" direct request), not something specific to labels. Sticker bulk-discount tiers are a second, independent tier list (`YeffoPrint_Sticker_Pricing::META_TIERS`) evaluated only against combined sticker quantity — a sticker order never counts toward the label discount threshold or vice versa, since the two products sit at completely different price points and mixing thresholds would misprice one or the other.
- **All sticker pricing knobs live as new meta on the same "one active" `yp_pricing_rule` post, not a second Pricing Rule CPT:** one Pricing Rules screen for the whole site (base/fee/label tiers, now also the custom-size rate, sheet/die-cut and shape dollar adjustments, and sticker tiers), matching `YeffoPrint_Pricing_Rule::get_active_rule_id()`'s existing "exactly one active rule" model rather than introducing a second single-record CPT with its own active-record logic to duplicate. The sticker bulk-tier repeater UI is a second, independent copy of `assets/admin/pricing-tiers.js` (`sticker-pricing-tiers.js`) rather than a second load of the same file — the original hardcodes one global config name and one set of DOM ids, so it can't run twice against two different tier lists on the same screen; matches this project's general preference for a small dedicated script per concern over a shared component abstracted before it's needed twice for the same purpose.
- **Materials are shared with a new scope flag, not split into a separate sticker Material CPT:** vinyl and holographic genuinely apply to both product lines; duplicating them as separate records risks the two drifting out of sync the way §4's Phase 4 entry already ruled out for `compatible_products`. `YeffoPrint_Commerce_Record_Meta::SCOPE` (`label` / `sticker` / `both`, defaulting to `label`) reuses the existing Material CPT, admin screen, image/description/price fields wholesale — new sticker-only materials (glitter, kraft, clear) just get created there with a different scope. `get_materials_for( $for )` centralizes the query (an explicit `NOT EXISTS` fallback to `'label'` only, so every pre-existing Material keeps working in the flow it already worked in without a migration, and never silently starts appearing in the sticker flow it was never reviewed for) — `class-custom-order-controller.php`'s existing label-form `options()` endpoint was updated to call it too, closing a real regression risk: without that fix, the first sticker-only Material an admin ever creates would have silently leaked into the label Custom Design form's picker.
- **What's deliberately not built yet:** the customer-facing `/custom-stickers/` form (still the Phase 10 "coming soon" placeholder), its REST submission endpoint, the hidden linked WooCommerce product(s) a sticker order would add to cart (mirroring `YeffoPrint_Custom_Design_Fee_Product`/`YeffoPrint_Custom_Order_Labels_Product`), and the cart-display (`YeffoPrint_Cart_Pricing::display_item_data()`) branch for a sticker line item. None of that is reachable yet — no sticker `CustomOrder` can be created until the submission endpoint exists — so this stage is safe and independently reviewable on its own, matching the phased-validation discipline the V1 and V2 builds both followed rather than shipping the whole feature in one unreviewed pass.

## QR code label field (direct request)

A new `qr_code` Template field type (`YeffoPrint_Field_Schema::TYPES`, alongside `text`/`textarea`/`color`) — a customer types a URL into the field, the configurator renders an actual scannable QR code in the live preview at that field's position, and staff can pull a print-ready PNG or PDF straight from the order screen for whichever URL a customer entered ("so I don't need to use a 3rd party site").

- **The QR encoder is a faithful line-for-line PHP port of Project Nayuki's reference `qrcodegen` library (MIT), not an independent implementation from the ISO/IEC 18004 spec:** `includes/lib/class-qr-code-gen.php`. A QR encoder is exactly the kind of code where a subtle bug (wrong Reed–Solomon generator polynomial, an off-by-one in the module-placement zigzag) produces something that still *looks* like a QR code but doesn't scan — unacceptable on a physical print product — so this stays a port of well-tested reference logic rather than something reasoned out from the spec by hand. Verified by cross-checking the PHP port's module grid, byte-for-byte, against the upstream Python reference (`pip install qrcodegen`, same author/algorithm) across ~70 cases spanning all four error-correction levels, all three relevant encoding modes (numeric/alphanumeric/byte, auto-selected same as upstream), version boundaries, and randomized fuzz inputs up to the byte-mode capacity ceiling — every case matched exactly after one real bug was found and fixed this way (see next entry). Not vendored as a Composer package — this plugin has no build-step/dependency-manager infrastructure anywhere (same reasoning as Custom Stickers' pricing engine staying hand-rolled rather than pulling in a library), and a single well-documented ~900-line file is easy to keep in one place and audit against the upstream original.
- **A real bug the cross-check caught, worth naming since it's a general Python→PHP translation trap:** the module-placement zigzag loop mutates its own loop-control variable inside the body (`if right <= 6: right -= 1`) to compute where to draw. In Python, `for right in range(size-1, 0, -2)` iterates a pre-materialized sequence, so that mutation has zero effect on which value comes next. PHP's C-style `for` re-reads the *live* variable on every step, so reusing it for both the loop control and the body's adjusted value silently corrupted the step size whenever that line fired — a version-2 symbol drew 550 modules instead of the correct 600, with the deficit scattered unpredictably through the data region rather than failing loudly. Fixed by giving the loop a dedicated control variable (`$right_raw`) and computing the adjusted value as a separate local (`$right`) each iteration, mirroring Python's actual semantics instead of its surface syntax. This is the reason the byte-for-byte cross-check existed at all rather than trusting a careful read-through — the ported code looked correct on inspection.
- **PNG rendering uses GD (`class-qr-renderer.php`), always black-on-white with no color options:** a colored or low-contrast QR code is a real scan-reliability risk on a physical product a customer's phone camera has to read under ordinary lighting — not a design choice worth exposing, unlike Material swatches or brand colors elsewhere on the site.
- **PDF rendering is a minimal hand-built single-page PDF, not a pulled-in PDF library — for the same "no dependency infrastructure" reason as the encoder itself, but with much lower correctness risk:** one FlateDecode 1-bit `DeviceGray` image XObject placed on a page sized to exactly the requested physical dimensions (no extra margin/layout — the file is a ready-to-place crop). Unlike QR encoding, a single embedded raster on one page is simple enough to construct correctly by hand from the base PDF spec. Verified two ways: `file` correctly identifies the output as "PDF document, version 1.4, 1 page(s)", and — the real test — PyMuPDF (a production PDF engine, no relation to this project) opened and rendered it, then every rendered pixel was compared against the same ground-truth QR grid the PNG was checked against; zero mismatches. The PNG path got the identical pixel-for-pixel check via Pillow.
- **One public REST endpoint (`GET /yeffoprint-core/v1/qr`, `class-qr-controller.php`) serves both the live preview and the admin download — not two separate endpoints:** QR rendering is a pure function of its input text, tied to no customer/order/auth context, so the configurator's `<img>` tag and the order screen's "Download PNG/PDF" links point at the exact same route (the latter with `download=1` for a `Content-Disposition: attachment` response) rather than needing a second, admin-only code path. Same reasoning as the existing public `/pricing/calculate` endpoint. Rate-limited per IP (10 min / 60 requests) and capped at 500 input characters before it ever reaches the encoder, mirroring the Phase 10 audit's rate limit on the unauthenticated custom-order upload endpoint — real CPU cost on an unauthenticated route is the same abuse shape either way.
- **The configurator debounces the live preview per QR field (400ms, keyed by field id), not per keystroke:** re-fetching a rendered QR image on every keystroke of a URL would be wasteful and would flicker mid-type; a field showing a dashed placeholder box (`.is-qr.is-empty`) until at least 4 characters are typed avoids firing requests for an obviously-incomplete URL. Matches the existing `pricingDebounceTimer` pattern in shape, keyed by field id (not a single shared timer) since a schema could in principle carry more than one QR field.
- **QR field values are validated as real URLs, not free text — `esc_url_raw()` + `wp_http_validate_url()` everywhere a value is read or written (`YeffoPrint_Field_Schema::sanitize()` and `sanitize_variants()`), same pattern as `color`'s `sanitize_hex_color()`:** restricting to the `http`/`https` schemes specifically (not just "well-formed URI") closes off a `javascript:`/`data:` URL ending up encoded into a QR code and then decoded by some downstream scanner/app in a context that trusts it — confirmed rejected by the same test pass that validated the valid-URL and required-field paths.
- **Order-screen download links reuse `YeffoPrint_Field_Schema::format_variant_summary()`'s sibling data path, not a new lookup:** `YeffoPrint_Order_Item_Meta::add_qr_download_links()` hooks `woocommerce_order_item_get_formatted_meta_data` (admin-only, gated on `is_admin()` — these links are a staff production aid, not something customer-facing order emails need), reading field types from the order's own frozen `_yp_template_snapshot.field_schema` rather than the Template's current schema — same "what was actually purchased" snapshot principle Phase 7 already established for pricing/size/material, so a QR field type changed or removed after the fact doesn't affect an already-placed order's download links.
- **"Every page shows homepage content" (live-site incident, not a code bug) — root cause was Settings → Permalinks silently reverted to "Plain," almost certainly during a pre-launch content cleanup pass that also deleted every Page:** worth logging since nothing about the symptom pointed at permalinks directly, and it cost a long diagnostic pass (browser/CDN cache, DB template overrides, deleted pages, rogue plugins — all real things to check, all ruled out one at a time) before the actual cause surfaced. The tell, once found: page source showed REST/AJAX URLs in the fallback `index.php?rest_route=...`/`?wc-ajax=...` form instead of the pretty `/wp-json/...` form — the giveaway that WordPress had no rewrite rules mapping *any* pretty path to anything, so every request (including `/wp-json/` itself, which is why it returned homepage HTML instead of JSON) fell through to WordPress's default query, the front page. Recreating the deleted pages didn't help because the pages were never the problem — the URL structure that would have pointed *at* them was gone. Fixed by switching Permalinks back to "Post name" and saving (which is a different action than just re-saving Permalinks with "Plain" still selected — that only reflushes the *current*, still-broken structure, which is why an early "try re-saving Permalinks" suggestion didn't resolve it). No code changed for this one.
- **Gallery card hover-swap removed (direct follow-up to the vial-mockup-leads change already logged above):** once the card's media box became sized/shaped for a standing vial photo rather than the flat label's 15:7 rectangle, the hover-revealed label image read as a badly-cropped strip inside that box — worse than not showing it at all. `blocks/template-card/render.php` now renders a single image (vial mockup, falling back to flat artwork only if no mockup is uploaded) with no hover state; `assets/css/patterns.css` drops the `--primary`/`--hover` opacity-crossfade rule pair accordingly. The flat label artwork itself isn't gone from the site — it's still exactly what the configurator's Label View on the actual template page renders; it's just no longer paired with the vial photo on gallery/homepage cards.
